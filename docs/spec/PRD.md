# 2. Product summary

KAIRO finds the access-control and secret-handling mistakes that AI coding assistants repeat, and explains each one in plain language with a tested fix.

A user connects a GitHub repository or uploads a project archive. KAIRO then runs three layers of analysis and merges the results into one report.

- **Static analysis** reads the source for hardcoded secrets, routes with no authentication, and unsafe query construction.
- **Logic review** gives a language model the relevant route, middleware and data model and asks whether the code enforces who may do what. This catches flaws that a pattern cannot, such as an endpoint that checks login but never checks ownership.
- **Dynamic testing** starts the application in an isolated sandbox and attempts login bypass, role tampering and cross-account data access using accounts the user supplies.

*Scan pipeline: three layers merged into one report*


| Stage | What happens |
| --- | --- |
| Intake and route inventory | A GitHub repository or ZIP archive is read and parsed into a route inventory that all three layers use. |
| Static analysis | Secrets, open routes, unsafe queries, configuration and token checks. |
| Logic review (optional) | AI-assisted review of ownership and role checks. The user can switch it off. |
| Dynamic testing (optional) | A sandboxed run with test accounts. It needs a start command from the user. |
| Merge and rate | Duplicates are removed, severity is set by a fixed rubric, and confidence is assigned. |
| Report | Web view, PDF, JSON and SARIF. |


Parsing the code produces a route inventory that all three layers use. Dynamic testing and logic review are optional, and the report states which layers ran.

Each finding carries a severity, a confidence level, a file and line, a reproduction note when it was confirmed dynamically, and a fix the user can apply. The product is built for people who did not write, and may not fully understand, the code they are about to ship.


# 3. Problem statement

AI coding assistants produce working applications quickly, but they rarely produce correct authorization, and the people shipping that code usually cannot tell the difference.


## What goes wrong

Broken Access Control is the first category in . Applications generated by assistants repeat a small set of its forms:

- Routes that never check whether the caller is logged in.
- Routes that check login but not ownership, so changing an ID in a URL returns another user's data.
- Role or permission fields accepted from the request body, so a standard user can promote themselves to administrator.
- Access control enforced only in the front end, with the API behind it left open.
- Secrets such as API keys, database URLs and service-role tokens committed to the repository or shipped in the client bundle.
- Backend-as-a-service rules left permissive, for example database tables with no row-level policy.

## Why it keeps happening

- An assistant optimizes for the feature the user asked for. Authorization is a cross-cutting rule that no single prompt mentions.
- Each generated file can be correct on its own. The flaw appears only when the route, the middleware and the data model are read together.
- The person prompting often cannot read the code well enough to notice a missing check, and does not know which tests would expose it.

These causes are working hypotheses. Section 15 defines the baseline study that tests them.


## Who is affected

People who ship applications without a security review: students, solo founders, freelancers, small agencies and builders of internal tools. Their end users carry the harm when personal data is exposed or accounts are taken over.


## Why current practice does not close the gap

Professional scanners assume the reader can interpret a rule identifier and a weakness number. Manual penetration tests cost more than these builders can pay and take longer than their release cycle. As a result, many applications reach real users with no security check at all.


## Evidence

This PRD cites no external prevalence statistics. The team will measure prevalence on its own labelled sample of AI-generated applications, as described in section 15.


# 4. Goals, non-goals and principles

The first release succeeds if a non-expert can scan an AI-generated web application and fix its serious access-control flaws without outside help.


## Goals


| ID | Goal |
| --- | --- |
| G1 | Detect the vulnerability classes in section 10 in AI-generated Node.js and Python web applications. |
| G2 | Give every finding a location, a plain-language explanation, a fix and a way to verify the fix. |
| G3 | Confirm findings by safe reproduction where possible, so users see evidence instead of warnings. |
| G4 | Keep user code and reports private by default, and test only what the user is authorized to test. |
| G5 | Operate as a real product: legal pages, accessible interface, documented API and reliable processing. |


## Non-goals

- Replacing professional penetration testing, or issuing any compliance certification.
- Scanning systems the user does not own or control.
- Covering every vulnerability class. The first release focuses on access control, authentication and secrets.
- Committing fixes to user repositories automatically. Suggested patches are shown, not applied.
- Producing a single composite security score.
- Scanning mobile apps, desktop apps or infrastructure-as-code.

## Product principles


| Principle | What it means in practice |
| --- | --- |
| Evidence over assertion | A finding states what was observed and where. Dynamic confirmation is shown when it exists. |
| Plain language first | Terms are defined where they first appear. A reader with no security background can follow every finding. |
| Authorized testing only | Active tests run in a sandbox or against a target whose ownership has been verified. |
| Honest about uncertainty | Every finding has a confidence level. A clean report never claims the application is secure. |
| Data minimization | Source code is read-only, kept for the shortest workable time and deleted on request. |
| Plain and trustworthy design | The interface looks like a professional tool. It uses no hype, no decoration for its own sake and no invented proof. |

| Persona | Who they are | Pain today | Priority |

| Freelancer or small agency developer | Ships client applications under deadline, often on a backend-as-a-service. | Cannot afford a penetration test per project and needs something to show the client. | Primary |

## Jobs to be done

- When I am about to share my application with real users, I want to know whether anyone can read other people's data, so I can launch without exposing them.
- When a scan reports a problem, I want the exact fix for my framework, so I can resolve it without first learning security.
- When I have fixed a problem, I want to re-run only that check and see it pass.
- When someone asks whether I checked security, I want a report I can hand over.
- When I connect my repository, I want to be sure my code is read, not changed, and not kept longer than needed.

# 6. Competitive landscape

Scanners aimed at AI-generated code already exist, so KAIRO competes on verified authorization testing and plain-language reporting, not on pattern coverage alone.


| Category | Examples | Strength | Gap for this audience |
| --- | --- | --- | --- |
| General static analysis | Semgrep, SonarQube, GitHub CodeQL | Broad rule coverage, CI integration, mature engines | Output is written for security engineers. Generic rules reason poorly about whether a route checks ownership. |
| Dynamic and manual testing | OWASP ZAP, Burp Suite | Real traffic, the professional standard | The operator must already know what to test and how to configure sessions and roles. |
| Scanners aimed at AI-generated apps | vibeward, vibe-hardening, VibeCheck | Fast, free, tuned to common mistakes, easy to run | Mainly pattern and configuration checks. Findings are generally not confirmed against a running application with several accounts. |


This comparison reflects what was publicly visible on 10 October 2026. Competitor features change and must be re-verified before any external publication.


## Where KAIRO is meant to differ

- **Authenticated, multi-account testing.** Cross-account data access and role tampering are tested with accounts the user supplies, so a finding can be confirmed instead of guessed.
- **Logic review tied to the full route.** The model reads the route, its middleware and the data model together, which is where ownership checks are missing.
- **A report written for a non-expert.** Every finding has a plain explanation, a fix for the user's framework and a re-check.
- **Explicit authorization and privacy controls.** Ownership is attested or verified before any active test, and source retention is short and visible.

These differences are hypotheses. They hold only if the benchmark in section 15 shows KAIRO finding real flaws that the pattern-based tools above miss.


# 7. Scope

Release 1 covers two ecosystems and three analysis layers end to end, and defers everything that widens the surface without strengthening the core promise.


## Release 1 (MVP)

- Sign-in with GitHub. No other identity provider.
- Project intake from a GitHub repository (public or private, read-only access) or a ZIP upload.
- Supported stacks: JavaScript and TypeScript with Express or Next.js route handlers, and Python with FastAPI or Flask.
- Static analysis for secrets, unauthenticated routes, unsafe query construction, insecure configuration and token misuse.
- AI-assisted logic review of ownership and role checks on routes.
- Dynamic testing in an isolated sandbox, using a start command and test accounts the user provides.
- Report as a web view, PDF, JSON and SARIF, with finding status tracking and re-scan.
- Privacy Policy, Terms and Conditions, security contact page, data export and account deletion.

## Release 2

- Pull request checks and a CI action that fails a build on chosen severities.
- Django and additional frameworks.
- Live Supabase and Firebase rule probing against projects whose ownership is verified.
- Testing a verified staging URL instead of a sandbox copy.
- Team workspaces with roles, and notifications by email and chat.
- A self-hosted model option for users who cannot send code to a third-party provider.
- Suggested fix as a pull request, opened only after explicit user approval.

## Out of scope

- Everything listed under non-goals in section 4.
- Billing and subscription management.
- Any scanning of targets whose ownership has not been attested or verified.

# 10. Vulnerability coverage

Release 1 targets thirteen vulnerability classes, weighted toward access control, and each class names the layer that is expected to find it.


| ID | Class | What it looks like | Found by | Default severity | Release |
| --- | --- | --- | --- | --- | --- |
| V01 | Missing authentication | A route returns data or changes state with no login check. | Static, Dynamic | High | 1 |
| V02 | Broken object-level authorization | A signed-in user reads or changes another user's record by changing an identifier. | Logic, Dynamic | High | 1 |
| V03 | Role tampering and privilege escalation | A standard user sets a role field or reaches administrator routes. | Static, Logic, Dynamic | Critical | 1 |
| V04 | Client-side-only access control | Hidden buttons or browser checks guard an API that is open. | Static, Logic | High | 1 |
| V05 | Hardcoded secrets and exposed credential files | Keys in source, committed environment files, a service-role key in the browser bundle. | Static | Critical | 1 |
| V06 | Token misuse | Signature not verified, the none algorithm accepted, a weak signing secret, no expiry. | Static | High | 1 |
| V07 | Weak credential handling | Plaintext or fast-hash passwords, cookies without security flags, no lockout. | Static | High | 1 |
| V08 | Injection through string-built queries | SQL or NoSQL queries assembled from request input. | Static | High | 1 |
| V09 | Missing rate limiting on sign-in | Unlimited password attempts. | Dynamic | Medium | 1 |
| V10 | Permissive cross-origin policy | Wildcard origin combined with credentials. | Static | Medium | 1 |
| V11 | Missing row-level security | Backend-as-a-service tables with no access policy. | Static | High | 1 |
| V12 | Mass assignment | A request body is bound to a model including protected fields. | Static, Logic, Dynamic | High | 1 |
| V13 | Debug mode and verbose errors | Stack traces or debug flags enabled in production settings. | Static | Medium | 1 |
| V14 | Unrestricted upload and path traversal | Uploads accept any type or name, and file paths are built from input. | Static | High | 2 |


## Severity rubric

Severity is assigned by a deterministic rubric applied to the finding class and its context. The model may propose a severity, but the rubric decides, so that the same flaw receives the same rating on every scan.


| Level | Meaning |
| --- | --- |
| Critical | Someone with no account or a low-privilege account can read or change many users' sensitive data, take over accounts or gain administrator access, with no special conditions. |
| High | The same kind of impact, but it needs a precondition such as a valid account, or it exposes one user's sensitive data at a time. |
| Medium | It weakens a defense or exposes limited information, and exploitation needs several conditions. |
| Low | A hardening gap with little direct impact. |
| Informational | An observation with no exploit path. |


## Confidence model

Severity says how bad a flaw would be. Confidence says how sure KAIRO is that it exists. The two are shown separately.


| Level | Definition |
| --- | --- |
| Confirmed | Reproduced against the running application. Request and response evidence is stored. |
| Likely | Two independent layers agree, or a logic finding cites a specific code path. |
| Possible | A single static or logic signal that has not been corroborated. |


# 11. Report requirements

The report is the product, so a non-expert must be able to read it in one pass and an engineer must be able to act on it without another tool.


## Report structure

- **Scan summary:** project, commit, date, which layers ran, which were skipped and why, and the model provider used.
- **Result overview:** counts by severity and confidence. There is no composite score.
- **Findings:** grouped by severity, then confidence.
- **Dismissed items:** findings the user marked as false positive or accepted risk, with the stated reason.
- **Scope and limits:** what was tested, what was not, and a statement that a clean result does not prove the application is secure.
- **Appendix:** the route inventory and a glossary of the terms used.

## Anatomy of a finding


| Element | Requirement |
| --- | --- |
| Title | Names the problem and where it occurs, for example "Any signed-in user can read another user's invoices". |
| Severity and confidence | Both shown as text labels, never by color alone. |
| Location | File, line and route. |
| What is wrong | Two to four plain sentences. |
| Why it matters | The consequence in the application's own terms. |
| Evidence | A code excerpt. For confirmed findings, the request and response with credentials redacted. |
| How to fix | Steps for the detected framework, with a code example. |
| How to verify | A re-check action and the result that means the fix worked. |
| Detected by | Static analysis, logic review, dynamic testing, or a combination. Logic review is labeled as AI-assisted. |
| References | The matching weakness identifier and OWASP category. |


## Requirements


| ID | Requirement | Priority |
| --- | --- | --- |
| FR-R1 | The web report is the primary format and every export contains the same findings. | Must |
| FR-R2 | PDF export uses print styles, tagged headings and the same section order as the web report. | Must |
| FR-R3 | JSON export follows a versioned, documented schema. | Must |

# 12. Non-functional requirements

A security product loses all credibility if it is itself insecure, so the platform's own security requirements are as binding as its features. Numeric targets are initial values to be confirmed by load and usability testing.


## Security of the platform


| ID | Requirement | Target or standard |
| --- | --- | --- |
| NFR-S1 | KAIRO is scanned by itself and by one independent tool before every release. | No open High or Critical findings at release |
| NFR-S2 | All traffic uses TLS. All stored data is encrypted at rest. | TLS 1.2 or higher |
| NFR-S3 | Every data query enforces ownership server-side. Cross-user access is covered by automated tests. | Tests fail the build on any cross-user read |
| NFR-S4 | Secrets live in a managed secret store, never in source control. User-supplied environment variables are encrypted per project. | Rotation procedure documented |
| NFR-S5 | Sandboxes run unprivileged with dropped capabilities, resource and time limits, no host mounts, and no access to cloud metadata endpoints. | Documented hardening checklist in the TRD |
| NFR-S6 | Outbound fetches block private, loopback, link-local and metadata addresses and re-validate after each redirect. | Covered by automated tests |
| NFR-S7 | Dependencies are pinned. Vulnerability alerts are enabled and a software bill of materials is produced per release. | Reviewed each release |
| NFR-S8 | Logs are structured and never contain source code, tokens or secrets. | Verified by a log-scrubbing test |


## Performance and reliability


| ID | Requirement | Target or standard |
| --- | --- | --- |

## Applicable law and timing

The product owner is based in India, so the Digital Personal Data Protection Act, 2023 applies. Its Rules were notified in November 2025 and take effect in phases, with the operational duties on data fiduciaries, including data principal rights, retention and cross-border transfer, expected in May 2027 according to commentary from  and . The two sources differ by a day or two on the exact date, so counsel must confirm it. KAIRO is designed to meet these duties from launch rather than wait for the deadline. If the product accepts users from the European Union or the United Kingdom, the GDPR is assessed under LR-11.


## Required contents of the Privacy Policy

The policy is written in plain language, carries a version and an effective date, and keeps a visible change history.

- Who operates the service, how to reach them, and who handles grievances.
- The data collected: GitHub identity (name, email address, avatar, numeric ID), repository contents read during a scan, test-account credentials and environment variables the user supplies, findings and evidence, technical logs such as IP address and user agent, and cookies.
- The purpose of each item and the basis for processing it, including the consent obtained.
- Where each item is stored and for how long, in a table.
- Every recipient of data, with purpose and region: the hosting provider, the model provider by name, and any email service.
- A plain statement of what is sent to the model provider, what is redacted first, that KAIRO does not use customer code to train models, and where the provider's own terms apply.
- The user's rights, how to exercise them, how consent is withdrawn, and how to escalate a grievance.
- A statement that the service is not directed at people under 18.
- A summary of security measures and a commitment to notify users of a breach that affects them.
- How changes are announced, and a contact address.

## Required contents of the Terms and Conditions

- Acceptance, eligibility and responsibility for the account.

# 15. Success metrics and baseline study

KAIRO is successful if it finds access-control flaws that comparable tools miss, and if a non-expert can understand and fix what it finds. The targets below are hypotheses to be revised after the baseline study.


| Metric | Definition | Initial target | How measured |
| --- | --- | --- | --- |
| Recall on seeded flaws | Share of known flaws in the benchmark that KAIRO reports | 80 percent or higher for V01, V02, V03 and V05 | Benchmark run per release |
| Precision, Confirmed findings | Share of Confirmed findings that are real flaws | 95 percent or higher | Manual review of every Confirmed finding in the benchmark |
| Precision, Likely findings | Share of Likely findings that are real flaws | 70 percent or higher | Manual review of every Likely finding in the benchmark |
| Advantage over baseline tools | Benchmark flaws in V02 and V03 found by KAIRO but missed by the baseline tools | Greater than zero | Same benchmark, run with default-configuration Semgrep and one scanner aimed at AI-generated apps |
| Time to first report | Median time from sign-in to a complete report for a new user with a sample project | Under 10 minutes without dynamic testing | Moderated usability sessions |
| Comprehension | Participants who explain a High finding in their own words and apply the fix unaided | At least 4 of every 5 participants | Moderated usability sessions |
| Fix verification rate | Share of High and Critical findings that reach Fixed after a re-check within 7 days | Set after a baseline is collected | Product data |
| Scan completion rate | Share of scans that end with a report | 95 percent or higher | Job records |
| Safety incidents | Active tests that affected anything outside the sandbox, or any exposure of user source | Zero | Incident log and audits |


## Baseline study

Sections 3 and 6 rest on assumptions about AI-generated applications. The baseline study tests them before the claims are repeated outside the team.

- Build a sample of applications from a fixed list of prompts across the supported stacks. Record the assistant, model, date and prompt for each.
- Add deliberately vulnerable applications with known flaws, and fixed counterparts of each.
- Have two reviewers label every flaw by class independently, then resolve disagreements.
- Measure how often each class occurs in the generated sample, and how KAIRO and the baseline tools perform on all of it.
- Publish the method and its limits, including sample size, which the implementation plan must set large enough to report results per class.

Only applications the team generated or that carry an open license are used. No one else's deployed system is scanned.


## Measurement and privacy

Product analytics are first-party and aggregated, are described in the Privacy Policy, and never contain source content or finding details that identify a user's application.


# 16. Assumptions, dependencies and constraints

Dynamic testing is the most assumption-heavy layer, because it only works when the application can be started and signed into without outside services.


## Assumptions

- Target users keep code on GitHub or can export a ZIP archive.
- The application starts from one command inside a Linux container, and its dependencies install from public registries.
- Test accounts can be created without third-party verification such as SMS codes or email links, or the user supplies a seed command that creates them.
- A model provider with acceptable data-handling terms is available at a workable cost.
- Users have the right to authorize testing of the project they submit.

## Dependencies

- GitHub for sign-in, the GitHub App and repository access, including its API rate limits.
- A model provider API for logic review, behind a replaceable interface.
- A container runtime with strong isolation for sandboxes.
- Hosting for the web application, API, workers and database.
- Open-source parsing and rule engines, subject to LR-10.

## Constraints

- The first release must be complete within one academic term and built by a small team.
- Operating cost must stay within free tiers or student credits during the term.
- The product has no legal entity yet, which affects the Terms, the grievance contact and contracts with providers. See section 19.
- Applications that depend on external sign-in providers, such as Google, cannot be fully tested in a sandbox without network access. They are reported as a limitation and not as a pass.

# 17. Risks and mitigations

The two risks that could end the product are misuse of the testing capability and a breach of stored reports, so both are controlled in the requirements and not left to policy text.


| ID | Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- | --- |
| R1 | Someone uses KAIRO to attack a system they do not own. | Medium | High | LR-1, LR-2, sandbox-only testing in Release 1, rate caps, LR-13, account suspension and an abuse contact. |
| R2 | A breach exposes stored findings and evidence, which describe weaknesses in users' applications. | Low | High | NFR-S1 to NFR-S8, short retention, encrypted storage, redacted evidence, and share views that omit evidence by default. |

# 20. Glossary, companion documents and sources

## Glossary


| Term | Meaning |
| --- | --- |
| Access control | The rules that decide who may see or change what in an application. |
| Authentication | Proving who a user is, usually by signing in. |
| Authorization | Deciding what a signed-in user is allowed to do. |

| Row-level security | Database rules that limit which rows each user can read or change. |
| SARIF | Static Analysis Results Interchange Format, a standard file format for scan results. |

| Seed command | A command that creates test accounts and sample data before testing. |
| Static analysis | Reading source code without running it. |
| Vibe coding | Building software mainly by prompting an AI assistant, with little manual review of the code. |
